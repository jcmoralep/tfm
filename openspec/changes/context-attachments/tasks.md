Standing rules baked into every task:

- **Lean tests.** Group same-rule cases in `[Theory]`; no reflection-shape tests; no label-by-label tests; keep rule, gate, round-trip and traversal tests. Existing tests (prompts, goldens, `ModuleBoundaryTests`, `FakeArtifactDrafterTests`) stay green with no edits beyond those listed.
- **Views.** CSS classes only: no `style=`, no `<script`, no new JS module. Grep every touched razor file.
- **Logs.** Never log file names, titles, URLs, note text, content types, file bytes, prompts or the key. Only request name, ids, kind, sizes, counts, durations, reason code, exception type (D9, D10, D11, D16).
- **Module boundary (D19).** Context sources never write `Conversation`, a bare `Initiative` or a bare `Artifact`; Context reaches Initiatives only through `GetInitiativeQuery`. Prompt literals in `Infrastructure/Assistant` and `Infrastructure/Artifacts` use the lowercase "attached" and never a capitalised `Attachment`.
- **Build and test commands** (every gate): `dotnet restore --ignore-failed-sources -p:NuGetAudit=false -p:WarningsNotAsErrors=NU1507`, then `dotnet build -c Release --no-restore` (zero code warnings), then `dotnet test -c Release --no-build`.
- **Chrome walkthroughs (S3, S4, S5, AGENTS 5.4).** Start MySQL with `docker compose` and temporary credentials, apply migrations, run the app with the seed user and `Assistant:Provider=Fake` (S5 adds one Gemini run), review `Logs/`, tear everything down (MySQL, app, and the scratch `App_Data/attachments` folder). Take plain-text notes of what was observed in each step; they are saved to Engram topic `sdd/context-attachments/chrome-notes` at the end of each walkthrough and written into `docs/evidencias/context-attachments-recorrido-chrome.md` in task F.3. No screenshots in the repository.
- **Docs placement.** README and `AGENTS.md` 4.7 and REQUISITOS RF-22, 23, 25, 75, 76, 77 are written in S4 (design file table); RF-14 and RF-24 and `docs/gemini-evaluacion.md` in S5. Group F re-reads them side by side and holds the evidence doc and the manual checks.
- **After apply.** A manual 3-lens code review and an independent verify run outside these tasks' commits.

## Reconciliation notes (design wins; the spec was aligned in this phase)

Every item below is a divergence between the spec files and `design.md` that I found by reading both in full. The tasks above follow the design. The matching spec lines were amended in this phase (`specs/context/spec.md`, `specs/assistant/spec.md`, `specs/initiatives/spec.md`); the design text rules if any spec line still disagrees. R20 to R23 are decisions about placement and gaps and needed no spec edit.

- **R1, S5 caps and order.** Spec: at most 5,000 per item and 20,000 in total, newest first, items beyond the total omitted. Design D16: 5,000 characters per item, **15,000** in total, **at most 10 items**, **oldest first**, the last item clipped and ending with `[recortado]`, at most 20,000 bytes read per file. Spec scenario "Caps and order" and the SPEC-CX Assumption "exact S5 caps are fixed in design" amended.
- **R2, text-like file selection.** Spec: `.txt`, `.md`, `.csv`. Proposal/exploration: content types `text/plain|markdown|csv`. Design D16: by **normalised extension** `.txt`, `.md`, **`.markdown`**, `.csv`, never the browser's content type. Spec requirement, RF-14 and RF-24 texts (`REQUISITOS.md` edit list) amended to list `.markdown`.
- **R3, `IFileStorage` contract and location.** Spec: save a stream, open, delete, and **report whether a key exists**; key list has no size cap argument. Design D4: `SaveAsync(key, content, maxBytes, ct)` returning bytes written and throwing `FileTooLargeException`, `OpenReadAsync` (null when missing), `DeleteAsync`; **no `Exists`**. Scenario "Round trip" uses open-returns-null for existence.
- **R4, invalid text.** Spec: a `.txt` with invalid UTF-8 is skipped and counted as skipped. Design D16: decoded as UTF-8 **with replacement**; only a missing or unreadable file is skipped. Scenario "Invalid text is skipped" replaced by "invalid UTF-8 is replaced, a missing file is skipped".
- **R5, storage configuration.** Spec: key `Storage:LocalPath`, default `Storage/Files`, resolved against the content root; `MaxFileSizeMb` any positive integer. Design D5, D6, D20: key **`Storage:LocalRootPath`**, default **`App_Data/attachments`**, resolved with `Path.GetFullPath` against the working directory, `.gitignore` gets `App_Data/`; `MaxFileSizeMb` an integer **from 1 to 50**; `S3` and any other value fail with fixed messages that never echo a value. Spec "Invalid max size" gains 51; `AGENTS.md` 4.7 text uses the design key.
- **R6, link title.** Spec: optional link title up to 120 characters, host as fallback name; scenario "Title fallback and limit". Design D9: `AddLinkAttachmentCommand(InitiativeId, Url)` and `CreateLink(..., url, ...)` carry **no title**; the row label is the URL host. Title requirement and scenario removed.
- **R7, list order.** Spec: listed newest first, scenario "Newest first". Design D8: `ListAsync` ordered by `CreatedAt` (ascending), and D16 "oldest first". The card shows the repository order, oldest first. Scenario renamed "Oldest first". Open point for the reviewer, not blocking: a newest-first display would be a one-line change in the view if preferred; the design is followed as written.
- **R8, download endpoint tests.** Spec tags "Headers on success", "Hostile content type and name" and "Uniform 404" as [UNIT] with a real HTTP result. Design Testing Strategy has no endpoint host and `Results.File` writes the headers; the name rule lives in `AttachmentFileName.Normalize` (D3). The HTTP-level parts are retagged **[UI]** (DevTools Network in 3.5); the unit halves are the `Normalize` Theory and the download-query null cases.
- **R9, explicit maximum size.** Spec tags "Maximum size is explicit" [UNIT]. The Razor call cannot be unit-tested (no bUnit). Design D7 and D13: `ContextLimits` is registered by Infrastructure and returned inside `ContextView.Limits`; the card passes `view.Limits.MaxFileBytes` to `OpenReadStream`. Scenario retagged: data half [UNIT] (the view carries the configured cap), call half [UI]/[DOC].
- **R10, delete order on storage failure.** Spec: if file deletion fails the row **stays** and a failure is reported; if the row delete fails after the file, log and report. Design D11: a storage failure logs a warning (ids and exception type only) and the **row is still deleted**; a row that is already gone gives `NotFoundException(ContextTexts.NotFound)`. Scenario "Storage failure keeps the row" becomes "Storage failure still removes the row".
- **R11, delete confirmation text.** Spec: the dialog names the item and warns it cannot be undone. Design D15: one `ConfirmPanel Destructive` for every kind with the text "¿Eliminar este elemento del contexto?". Scenario "Delete confirmation" amended to the design text.
- **R12, name sanitising location.** Spec: a sanitising function applied by the download endpoint on every response, with a table and an RFC 5987 form. Design D3 and D12: the name is normalised once at creation (`AttachmentFileName.Normalize`, an empty result becomes `archivo`), and `Results.File` writes `Content-Disposition: attachment` with `filename*`. The spec statement "display name MUST NOT be empty" becomes "an empty name becomes `archivo`".
- **R13, S5 scope of the context.** Spec and proposal: the assistant "and the drafter" receive it; the draft request carries it for all documents. Design Corrections table, D17: assistant turn plus **Spec, Brief and PRD only**; `ArchitecturePrompt`, `EpicsPrompt` do not change and `DraftRequestAsync` fills it for those three types. SPEC-AS "Draft call carries it too" scoped to Spec, Brief and PRD, with a scenario that the Architecture and Epics requests carry none.
- **R14, where the block is assembled.** Spec and SPEC-AS: the caller passes an already-neutralised string to the Gemini client, which places it as a separate section "after the transcript data and before the final task text"; the client logs the three counts. Design D16 to D18: `AssistantPrompt` and `DraftPrompt` append a `<context>` block built from `ContextExcerpt` lists to the user content, both through one shared helper, `Infrastructure/Gemini/ContextPrompt.cs` (it sits outside the module folders, so the boundary scan does not read it); `GeminiClient` is not modified. The block is appended at the end of the user content (position is the design's "appended"), keeping existing prompts byte-identical when there is no context.
- **R15, context counts logging.** Spec: the Gemini client logs items sent, items skipped and characters sent. Design has no client change; the counts are logged by the `GetContextForAssistant` handler (it alone knows the skipped count). SPEC-AS "Logging redaction" amendment and "Context counts without content" scenario point at the query handler; no content is logged either way.
- **R16, titles and names in the block.** Spec: each item has its own `<context>` element with kind and sequence number only; no file name, title, URL or id; scenario "No names or ids in the block". Design D16 and D18: **one** `<context>` block; each item is introduced by `--- note: {Line(title)}` or `--- file: {Line(name)}`, so titles and file names do appear (neutralised, single line); ids and URLs never do (links are not sent). Scenarios "No names or ids in the block" and "No identifiers or names" amended to "no ids and no URLs".
