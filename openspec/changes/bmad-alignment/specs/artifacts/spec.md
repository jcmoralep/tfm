# Delta for Artifacts (bmad-alignment)

**Baseline.** The capability `artifacts` is NOT in `openspec/specs/` yet. The baseline of this delta is `openspec/changes/artifact-generation/specs/artifacts/spec.md` (status done, verify PASS WITH WARNINGS). BMAD has no archive or global spec merge, so artifact-generation is not archived: every MODIFIED requirement below is written in FULL (complete replacement text, same name as in the baseline) and replaces the baseline requirement of the same name; every requirement of the baseline that is not named here stays as it is. Source requirements: RF-20, RF-35, RF-36, RF-41 to RF-44, RF-47, RF-51 to RF-66, RN-03, RN-06 to RN-08 (REQUISITOS.md; RF-61 to RF-66 and RN-08 are the authority).

Scenario tags: **[UNIT]** xUnit at validator, handler or pure-class level (hand-written doubles, no bUnit). **[UI]** manual-only check in Chrome. **[DOC]** documentation deliverable checked by reading the file. Terminology as in the baseline. Added terms: an **open question** is a Q-n line of the questions section (Preguntas pendientes in Brief, Preguntas abiertas in PRD and Spec). **Unassigned** is defined in "Open-question triage line". **Gate** is the approval check of "Approval and completion". Message wording is a proposal unless marked verbatim.

## ADDED Requirements

### Requirement: Open-question triage line (RF-61, RF-43, RF-20, RN-03)

Every open question MUST be one Markdown list line `- **Q-n**: <text> (Responsable: <owner>; Revisar: <revisit>)`, so the Markdown stays the only source of truth (no table, no migration). The suffix is read only at the END of the line (trailing whitespace ignored); everything before it is the question text, which MAY itself contain parentheses. Questions generated by the platform MUST end with the default `(Responsable: por asignar; Revisar: por definir)`.

A pure reader of the Markdown MUST return, in document order, for each open question: id, text, owner, revisit text and whether it is unassigned. It MUST ignore fenced code blocks and the assumption index, and MUST recognise a definition the same way the format checker does (optional list marker, optional bold, valid hyphenated number from 1). A question is **unassigned** when the suffix is missing or malformed, or the owner is empty (after trimming) or equals `por asignar`, or the revisit text is empty or equals `por definir` (comparison ignores case and surrounding spaces). Both data are required: one of them unassigned makes the question unassigned.

Written values (by the assign command) MUST obey: owner at most 60 characters after trimming and revisit text at most 80 characters after trimming, both with inner whitespace collapsed and containing none of `(`, `)`, `;`, `[`, `]`, `*`, `|`, `\` or a line break (one rule for both fields). Suggested owner areas offered to the user: Legal, TI, Finanzas, Quien propone la iniciativa; any other text is accepted. No phase flag, blocking flag or question state exists.

### Requirement: Approval gate on open questions (RF-62, RN-08, RF-59)

A document MUST NOT move from Draft to Approved while any open question is unassigned. The rejection MUST name them in document order, without repeats, with the verbatim text "Asigne un responsable y una condición de revisión a las preguntas pendientes antes de aprobar: Q-1, Q-3." and nothing is changed. The gate runs only inside the Draft-to-Approved branch of approve, after the ownership, version and availability checks. Therefore: re-approving an already Approved document at the same version MUST still succeed (idempotent) and MUST still complete the initiative when the set is approved and the initiative is Planning (CompletionPending retry), even if that document still has unassigned questions (documents approved before this change are grandfathered and are not reopened). Format warnings remain non-blocking (RF-59). Editing an Approved document returns it to Draft, so the gate applies again at its next approval. Regeneration returns every question to the unassigned default.

The document view MUST expose the open questions (id, text, owner, revisit, unassigned) and the ids of the unassigned ones (`UnassignedQuestions`). `CanApprove` MUST be false while `UnassignedQuestions` is not empty; the other flags (`CanEdit`, `CanRegenerate`, `CompletionPending`) are unchanged. The page MUST tell the user why Aprobar is disabled.

### Requirement: Assign question owners command (RF-63, RF-54)

The system MUST provide `AssignQuestionOwnersCommand` with the initiative id, artifact type, `ExpectedVersion` and a list of entries (question id, owner, revisit text). It MUST rewrite only the suffix of the listed Q-n lines, leaving every other character of the document unchanged. An entry whose owner or revisit text is empty after trimming MUST write the default (`por asignar` / `por definir`) for that field. Rejections (Spanish; nothing stored): an id with no open question, "La pregunta Q-9 no existe en este documento."; an empty entry list, "No hay preguntas para guardar."; a duplicated entry, "Hay preguntas repetidas en el envío."; an owner or revisit text breaking the limits of the triage line, "El responsable no puede superar los 60 caracteres." / "La condición de revisión no puede superar los 80 caracteres." / "El responsable no puede contener paréntesis, corchetes, comillas invertidas, ni los signos ; * | \ < >, ni caracteres de control o saltos de línea." / the same sentence for "La condición de revisión" (both fields share one character rule: no `( ) ; [ ] * | \ < >` or backtick, no control or invisible format characters); a result over the content cap, the baseline cap message.

When the rewritten content equals the stored content (after normalization) the command MUST succeed without changing version, status or times (no-op). Otherwise it MUST follow the edit rules: version +1, status Draft, approval time cleared, update time refreshed, and, if the initiative is ReadyToBuild, reopen it to Planning (before the save, as an edit does). It MUST use the same ownership, not-found, required-set, generated and version checks and the same conflict message as saving content, and MUST persist nothing in the initiative on conflict. The command and its result MUST NOT write owner or revisit text to logs and MUST redact them in their string form.

### Requirement: Generated content structure per document (RF-16, RF-36, RF-38, RF-40, RF-44, RF-61, RF-64)

`IArtifactDrafter` MUST produce the Markdown for a type from the initiative's name and description, its depth and the conversation answers. Each generated document MUST contain these sections, in this order, with these Spanish headings:

- **Brief**: Resumen ejecutivo, El problema, La solución, Qué lo hace distinto, A quién sirve, Criterios de éxito, Alcance, Visión, Índice de suposiciones, Preguntas pendientes.
- **PRD**: 0 Propósito del documento, 1 Visión, 2 Usuario objetivo (2.1 Trabajos por hacer, 2.2 No usuarios, 2.3 Recorridos clave), 3 Glosario, 4 Funcionalidades, 5 No objetivos, 6 Alcance del MVP (6.1 Dentro, 6.2 Fuera), 7 Métricas de éxito, 8 Preguntas abiertas, 9 Índice de suposiciones.
- **Spec**: Por qué, Capacidades, Restricciones, No objetivos, Señal de éxito, Índice de suposiciones, Preguntas abiertas.

Numbering MUST follow RF-44 with a hyphen and a number for every element, numbered in document order from 1 and without gaps within the generation: functional requirements `FR-n` (Capacidades of the Spec and Funcionalidades of the PRD, one per capability item), non-functional `NFR-n`, success metrics `SM-n` (Criterios de éxito of the Brief, Métricas de éxito of the PRD, Señal de éxito of the Spec), assumptions `A-n` (inline as `[ASSUMPTION: A-n]` followed by its text), pending questions `Q-n`. User journeys `UJ-n` are part of the scheme and valid in edited documents, but the generator MUST NOT write any. Each answer MUST be split into one item per non-empty line (list markers removed); an answer on a single line yields one item. At most 20 items are written per answer, followed by one plain line "y N más." when the answer had more, so many tiny lines cannot exceed the content cap. A "nothing" quick reply ("Ninguno", "Ninguno que yo sepa", "Nada por ahora", "Nada especial") MUST become one explanatory sentence without an identifier (for example "No se indicaron integraciones."), never an FR or NFR; the other quick replies (for example "Ambos") keep their label as text. The document MUST use the user's own words for the items, and MUST NOT present invented facts as certain.
(Previously: the PRD yielded one `UJ-n` per person in the users answer with a shared assumption (decision D1, now superseded), and Q-n lines had no owner or revisit suffix.)

Mapping of answers to sections (the sections not listed take an assumption):
- Brief: idea feeds Resumen ejecutivo and La solución; problem feeds El problema; users feeds A quién sirve; success feeds Criterios de éxito (`SM-n`); out of scope feeds Alcance (outside); Qué lo hace distinto, Visión and the inside of Alcance carry `[ASSUMPTION: A-n]`.
- PRD: idea and initiative name feed Propósito and Visión; users and problem feed Trabajos por hacer; Recorridos clave is not fed by any answer and holds the single assumption of "PRD key journeys section without markers" (no `UJ-n`, whatever the users answer); capabilities feed Funcionalidades (`FR-n`) and Alcance dentro (the line "Todas las funcionalidades de la sección 4.", annotated with the priorities answer when present); constraints and qualities feed `NFR-n` items under a "Requisitos no funcionales" feature of Funcionalidades; integrations and teams (Large) feed `FR-n` items under an "Integraciones" feature, each phrased as a requirement ("Debe integrarse con <sistema o equipo>"); out of scope feeds No objetivos and Alcance fuera; success feeds Métricas (`SM-n`). Glosario and No usuarios carry `[ASSUMPTION: A-n]` when nothing feeds them.
- Spec: idea, users and problem feed Por qué (the users go in one bullet, "Quién lo usará", joined by semicolons); capabilities feed Capacidades (`FR-n`); out of scope feeds No objetivos (at least one item); success feeds Señal de éxito (`SM-n`); Restricciones carries `[ASSUMPTION: A-n]` because Small asks no constraints topic.

Every section with no feeding answer MUST carry at least one `[ASSUMPTION: A-n]` marker instead of being left empty. The Índice de suposiciones MUST list every `A-n` of the document with its text, and Preguntas pendientes / Preguntas abiertas MUST list every `Q-n`, each line ending with the triage suffix of "Open-question triage line" (default `(Responsable: por asignar; Revisar: por definir)`).

### Requirement: Format warnings from the Markdown (RF-43, RF-44, RF-56, RF-59)

The system MUST derive format warnings by reading the Markdown on every read and every save, returning at most 50 of them followed by one final entry "y N avisos más." when there are more; a token without a hyphen ("Q4", "A4", "SM2") followed by prose is an ordinary word and MUST NOT be reported, while "FR1", "NFR1" and "UJ1" and any hyphenated attempt ("FR -1", "FR-", "FR-01", "fr-1", "NFR-x") are; warnings MUST never block saving or approving and MUST never alter or lose text. The parser MUST detect, per document type: a required section heading missing; an identifier of the kinds FR, NFR, UJ, SM, A or Q written without hyphen or number (for example "FR1", "FR-", "NFR-x") where a definition is expected; the same identifier defined twice; an `[ASSUMPTION: A-n]` marker whose A-n is absent from the Índice de suposiciones, or an index entry without a marker in the text; a Q-n or A-n numbered with zero. The rule that numbers are never reused or reordered on edits (RF-44) cannot be verified without history and MUST NOT be reported as a warning. An unassigned open question, a missing or malformed `(Responsable: …; Revisar: …)` suffix and the default suffix are NOT format warnings (they are handled by the approval gate, RF-59/RF-62). Warnings MUST be in Spanish, name the kind of problem and the identifier or heading, quote a short excerpt of the offending line (about 50 characters, without markup characters) instead of a line number, and be returned in document order. The structured index (items table, states) is out of scope.
(Previously: "owners and states" were out of scope of the index and nothing was said about the suffix.)

### Requirement: Optimistic concurrency (RF-17, RF-63)

Every command that changes a document (save, regenerate, approve, assign question owners) MUST carry `ExpectedVersion`. If the stored version differs, the command MUST fail with the conflict message "El documento cambió en otra pestaña. Si estaba editando, su texto sigue en el cuadro: cópielo, cancele y edite de nuevo la versión actual." and persist nothing, in the initiative as well. The version MUST act as the concurrency token of the row so two simultaneous writers cannot both succeed. A conflict MUST NOT discard the text typed in the editor or the values typed in the question panel, and each of them MUST keep sending the version its text was loaded from, so saving again conflicts again until the person cancels and edits the current version (the typed text is never silently saved over the other tab's change).

### Requirement: Approval and completion (RF-07, RF-19, RF-52, RF-59, RF-62, RN-01, RN-06, RN-08)

Approving MUST be a manual action of the owner on a Draft document with the expected version; it MUST set status Approved and the approval time, MUST NOT change the version and MUST NOT depend on the format warnings (a document with warnings can be approved; the warnings are shown in the confirmation). It MUST depend on the open-question gate: a Draft document with any unassigned open question MUST be rejected (see "Approval gate on open questions"), which is not a format warning. Approving MUST also require that the coverage of the document still holds (it is available per the Availability rules), so undoing a Planificar answer after generating takes the approval away until the topic is answered again; it is rejected with the existing "topics uncovered" text, and the initiative MUST NOT be completed while any document of the level is uncovered. Approving an Approved document at the same version MUST succeed without changes (idempotent) while the coverage holds, without evaluating the open-question gate. When, after an approval, every type of the required set of the initiative's level is Approved, the system MUST mark the initiative ReadyToBuild through the `initiatives` idempotent operation; otherwise the initiative status MUST NOT change. Large MUST NOT reach ReadyToBuild in this change because Architecture and Epics-and-stories cannot exist. If marking ready fails after the approval was stored, the approval MUST stay and a later approve or completion check MUST retry the transition (the retry is never blocked by the gate). No document MUST be Approved by any path other than this action.
